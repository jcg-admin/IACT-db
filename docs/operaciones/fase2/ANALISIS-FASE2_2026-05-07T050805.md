## H-ANAL-001 — Inconsistencia temporal base_ivr_detalle vs base_ivr_clientes

**Severidad: ALTA**

### Que se descubrio

```sql
-- Cobertura actual tras Fase 2
SELECT
    (SELECT COUNT(DISTINCT fecha) FROM base_ivr_detalle
     WHERE trimestre='Q01_25') AS meses_en_detalle,
    (SELECT MIN(fecha) FROM base_ivr_detalle WHERE trimestre='Q01_25') AS detalle_desde,
    (SELECT MAX(fecha) FROM base_ivr_detalle WHERE trimestre='Q01_25') AS detalle_hasta,
    (SELECT COUNT(*) FROM base_ivr_clientes WHERE trimestre='Q01_25') AS filas_clientes;
```

```
meses_en_detalle  detalle_desde  detalle_hasta  filas_clientes
1                 202501         202501         3
```

`base_ivr_detalle` tiene SOLO enero (1 mes). `base_ivr_clientes` tiene el
quarter completo (Q1 2025 = 3 meses). Son temporalmente inconsistentes.

### Por que ocurrio

El plan disenno T-031 y T-034 con rangos de fecha intencionalmente distintos:

- **T-031** (detalle): `sp_etl_base_detalle('Q01_25','2025-01-01','2025-01-31',...)` — solo enero
- **T-034** (clientes): `sp_etl_base_clientes('Q01_25','2025-01-01','2025-03-31',...)` — Q1 completo

Ambas tareas se ejecutaron exactamente como el plan indica. La inconsistencia
es consecuencia directa del diseno de las tareas de prueba, no un error
de ejecucion.

### Por que es un problema

```sql
-- Datos actuales en base_ivr_clientes
SELECT segmento, clientes_unicos FROM base_ivr_clientes WHERE trimestre='Q01_25';
```

```
segmento    clientes_unicos
nacional_A  22652
nacional_B  14802
puebla      12542
```

Estos clientes provienen de `tbl_historico_t1_2025` con rango 2025-01-01 a
2025-03-31 (90 dias). En cambio, `base_ivr_detalle` solo tiene enero (31 dias).

Cualquier query que cruce detalle con clientes para Q01_25 estara comparando
datos de periodos diferentes. Por ejemplo, si un reporte de clientes dice
22,652 clientes en nacional_A, pero el detalle dice 17,292 llamadas, la
inconsistencia oscurece el analisis.

```sql
-- Clientes unicos reales por periodo en la fuente
SELECT
    COUNT(DISTINCT CASE WHEN dFecha BETWEEN '2025-01-01' AND '2025-01-31'
          THEN cTelefono_Origen END) AS clientes_solo_enero,
    COUNT(DISTINCT cTelefono_Origen) AS clientes_q1_completo
FROM tbl_historico_t1_2025;
```

```
clientes_solo_enero  clientes_q1_completo
17291                49984
```

`base_ivr_clientes` dice 49,996 clientes, la fuente dice 49,984. La diferencia
de 12 se explica en H-ANAL-007.

### En produccion esto no ocurre

Cuando `sp_etl_maestro` ejecuta el ETL normalmente, usa las mismas fechas
para ambos SPs:

```sql
-- Fragmento de sp_etl_maestro
CALL sp_etl_base_detalle(v_quarter, v_inicio, v_fin, v_table, v_step_id);
CALL sp_etl_base_clientes(v_quarter, v_inicio, v_fin, v_table, v_step_id);
```

Ambos SPs reciben `v_inicio` y `v_fin` identicos. La inconsistencia solo
existe en el sandbox de pruebas porque T-031 y T-034 se ejecutaron
individualmente con rangos distintos.

### Accion requerida

Antes de ejecutar Fase 3 (backfill), corregir el estado del sandbox:

```sql
-- Opcion A: completar el detalle con los meses faltantes (feb y mar)
CALL sp_etl_base_detalle('Q01_25','2025-02-01','2025-03-31',
     'tbl_historico_t1_2025', NULL);

-- Verificar que detalle ahora cubre el quarter completo
SELECT fecha, SUM(total_llamadas) AS total
FROM base_ivr_detalle WHERE trimestre='Q01_25'
GROUP BY fecha ORDER BY fecha;
-- Esperado: 202501, 202502, 202503
```

```sql
-- Opcion B: limpiar ambas tablas y dejar que Fase 3 las llene correctamente
DELETE FROM base_ivr_detalle WHERE trimestre='Q01_25';
DELETE FROM base_ivr_clientes WHERE trimestre='Q01_25';
-- La Fase 3 (T-040 backfill Q01_25) llenara ambas con el quarter completo
```

**Recomendacion: Opcion B.** El backfill de Fase 3 es el mecanismo
correcto para poblar datos de produccion. Las pruebas de Fase 2 se
hicieron correctamente, la inconsistencia es inherente al diseno de las tareas.

**Impacto en el estado actual del sandbox:** ALTO. Los SPs de reporte
que usen Q01_25 mostraran datos parciales hasta que se ejecute Fase 3.

## H-ANAL-002 — T-037 criterio formal incumplido

**Severidad: MEDIA**

### Que dice el plan

```
Criterio: 3 registros de paso.
          Ningún RUNNING persistente.
Esperado: registros para 'maestro', 'etl_base_detalle', 'etl_base_clientes'
```

### Que hay en job_execution_log

```sql
SELECT id, step_name, status, records_procesados, duracion_seg, ejecutado_por
FROM job_execution_log ORDER BY id;
```

```
id  step_name  status   records_procesados  duracion_seg  ejecutado_por
1   maestro    SUCCESS  0                   NULL          test_t036
2   maestro    SKIP     0                   0             evt_etl_diario
```

Solo 2 registros, ambos con `step_name='maestro'`. Los checkpoints
`etl_base_detalle` y `etl_base_clientes` nunca se generaron.

### Por que ocurrio

En T-036, se inserto un registro RUNNING fake para probar la deteccion
de concurrencia. Cuando se llamo `CALL sp_etl_maestro()`, el SP detecto
el RUNNING y emitio SKIP sin ejecutar los sub-SPs. Por lo tanto los
checkpoints de detalle y clientes nunca se activaron.

El criterio de T-037 es dependiente de que sp_etl_maestro haya completado
exitosamente, lo que requiere que no haya concurrencia. Pero T-036 y T-037
son dependientes en el mismo log, y T-036 deja SKIP que bloquea T-037.

### Lectura del codigo de sp_etl_maestro

```
Si RUNNING en ultimas 6h → INSERT SKIP → LEAVE (no ejecuta sub-SPs)
Si no RUNNING            → INSERT RUNNING maestro
                         → INSERT RUNNING etl_base_detalle → CALL sp_etl_base_detalle
                         → INSERT RUNNING etl_base_clientes → CALL sp_etl_base_clientes
                         → UPDATE maestro a SUCCESS/PARTIAL
```

Para generar los 3 checkpoints se necesita una ejecucion sin RUNNING previo.

### Accion requerida

Los 3 checkpoints se verificaran en Fase 3, tarea T-040, que ejecuta
`sp_etl_historico(2025,1)`. Ese SP llama internamente al maestro en
condiciones limpias. Anotar esta verificacion pendiente en el documento
de Fase 3.

## H-ANAL-003 — sp_etl_validar no detecta inconsistencia temporal

**Severidad: MEDIA**

### Que hace sp_etl_validar

```sql
-- Logica interna del SP (obtenida de information_schema.routines)
SELECT COUNT(*), SUM(total_llamadas) INTO v_count_det, v_sum_llamadas
FROM base_ivr_detalle WHERE trimestre = p_quarter;

SELECT COUNT(*) INTO v_count_cli
FROM base_ivr_clientes WHERE trimestre = p_quarter;

-- Los 3 checks son:
-- 1. v_count_det > 0
-- 2. v_count_cli = 3
-- 3. v_sum_llamadas > 0
```

### El punto ciego

El validador NO verifica que `base_ivr_detalle` y `base_ivr_clientes`
cubran el mismo rango de fechas. Paso correctamente con:

- `base_ivr_detalle`: 1947 filas de ENERO (1 mes, 17,292 llamadas)
- `base_ivr_clientes`: 3 filas del QUARTER COMPLETO (3 meses, 49,996 clientes)

El resultado fue `@ok=1` — validacion exitosa sobre datos inconsistentes.

### Por que esto importa

Si en produccion un mes falla y el ETL solo carga 2 de 3 meses en detalle,
pero clientes se cargo completo, sp_etl_validar marcaria SUCCESS cuando
en realidad los datos son parciales. El `job_execution_log` mostraria
los checkpoints de detalle y clientes como SUCCESS, pero el detalle
estaria incompleto.

### Mejora sugerida para sp_etl_validar

```sql
-- Agregar verificacion de cobertura de fechas
-- Ejemplo para verificar que detalle cubre al menos el mismo rango que clientes
DECLARE v_min_fecha VARCHAR(6);
DECLARE v_max_fecha VARCHAR(6);

SELECT MIN(fecha), MAX(fecha)
INTO v_min_fecha, v_max_fecha
FROM base_ivr_detalle WHERE trimestre = p_quarter;

-- El quarter deberia tener datos en los 3 meses: YYYYMM01, YYYYMM02, YYYYMM03
-- Verificacion simple: al menos 3 meses distintos
IF (SELECT COUNT(DISTINCT fecha) FROM base_ivr_detalle
    WHERE trimestre=p_quarter) < 3 THEN
    SET v_msg = CONCAT(v_msg, 'ADVERTENCIA: detalle incompleto — solo ',
        (SELECT COUNT(DISTINCT fecha) FROM base_ivr_detalle WHERE trimestre=p_quarter),
        ' mes(es) de los 3 esperados. ');
END IF;
```

Esta mejora se puede implementar en `sp_etl_pipeline.sql` antes de Fase 3.
No es bloqueante para el backfill, pero mejora la deteccion de problemas.

## H-ANAL-004 — T-019 path de ejecucion difiere del plan; crash expone riesgo operacional

**Severidad: MEDIA**

### Path del plan vs lo ejecutado

El plan define T-019 como un test atomico en 4 pasos:

```
PLAN:
  1. Crear backup de ivr_es_dia_semana
  2. Reemplazar con funcion rota (siempre TRUE)
  3. Reprocesar enero → medir pct=100%
  4. Restaurar desde backup → reprocesar → medir pct=74.5%
```

Lo que ocurrio en la ejecucion:

```
EJECUTADO:
  Intento 1: crash de sesion bash (heredoc + comentarios SQL)
             → la funcion quedo en estado desconocido
  Intento 2 (archivo SQL con DELIMITER):
             → sabado_roto=1, pct_roto=100.0% OK
             → crash durante restauracion (backup ya eliminado del intento 1)
  Restauracion de emergencia:
             → mysql < funciones_utilidad.sql (redespliegue completo)
             → DELETE + CALL sp_etl_base_detalle para reprocesar enero
  Verificacion final: pct=74.5% (correcto)
```

### Resultados validos, trayectoria diferente

Los valores obtenidos son correctos:
- `pct_roto = 100.0%` confirma que la funcion rota produce datos incorrectos
- `pct_recuperado = 74.5%` confirma la recuperacion completa

Pero el paso "restaurar desde backup" fue reemplazado por "redesplegar desde SQL".
En produccion, ambas opciones producen el mismo resultado. En un test de CI/CD,
la diferencia importa porque expone un riesgo.

### Riesgo operacional identificado

Si T-019 se ejecuta en produccion y la sesion cae a mitad del test:

1. `ivr_es_dia_semana` queda en estado invalido (apunta a backup eliminado)
2. El SP sigue aceptando llamadas sin error (MariaDB no valida el cuerpo)
3. Pero al ejecutarse retorna NULL o error, corrompiendo silenciosamente
   todos los nuevos registros ETL hasta que se detecte
4. Los datos corruptos solo son detectables por T-018 (ratio fuera de 65-80%)

### Recomendacion

Antes de ejecutar T-019 en produccion, verificar que el procedimiento
de restauracion de emergencia esta documentado y probado:

```bash
# Restauracion de emergencia si T-019 falla a mitad
mysql --socket=/run/mysqld/mysqld.sock ivr_legacy \
    < provisioners/mariadb/funciones_utilidad.sql

# Verificar que la funcion es correcta
mysql --socket=/run/mysqld/mysqld.sock ivr_legacy -e "
SELECT ivr_es_dia_semana('2025-01-04') AS sabado_debe_ser_0,
       ivr_es_dia_semana('2025-01-06') AS lunes_debe_ser_1;"
```

Adicionalmente, considerar envolver T-019 en una transaccion o ejecutarlo
en una BD de staging, nunca directamente en produccion con datos reales.

## H-ANAL-005 — Registro fake de T-036 contamina job_execution_log

**Severidad: BAJA**

### Estado actual del log

```sql
SELECT id, step_name, status, records_procesados, ejecutado_por, duracion_seg
FROM job_execution_log ORDER BY id;
```

```
id  step_name  status   records_procesados  ejecutado_por  duracion_seg
1   maestro    SUCCESS  0                   test_t036      NULL
2   maestro    SKIP     0                   evt_etl_diario 0
```

El registro `id=1` con `ejecutado_por='test_t036'` es ruido de prueba.
El plan indicaba `UPDATE ... SET status='SUCCESS'` como cleanup, pero
un `DELETE` habria dejado el log mas limpio.

Adicionalmente, `duracion_seg=NULL` en id=1 porque el registro fue
insertado directamente (sin pasar por el flujo normal del SP que actualiza
`end_time`). La columna `duracion_seg` es calculada automaticamente cuando
`end_time` tiene valor — como se inserto sin `end_time`, queda NULL.

### Por que duracion_seg=NULL importa

Si alguien analiza el log para calcular tiempos de ejecucion, un NULL
en `duracion_seg` puede confundir. Los registros de produccion siempre
tendran `duracion_seg` calculado porque el SP actualiza `end_time`.

### Accion

En Fase 3, antes de ejecutar el backfill, limpiar el registro de test:

```sql
DELETE FROM job_execution_log WHERE ejecutado_por='test_t036';
-- Verificar
SELECT COUNT(*) AS registros_post_limpieza FROM job_execution_log;
-- Esperado: 1 (solo el SKIP de T-036)
```

## H-ANAL-006 — Seed tiene ~100% de telefonos unicos

**Severidad: BAJA**

### Datos

```sql
SELECT COUNT(*) AS total_filas,
       COUNT(DISTINCT cTelefono_Origen) AS telefonos_unicos,
       ROUND(COUNT(DISTINCT cTelefono_Origen)*100.0/COUNT(*),1) AS pct_unicidad
FROM tbl_historico_t1_2025;
```

```
total_filas  telefonos_unicos  pct_unicidad
50000        49984             100.0
```

49,984 telefonos unicos en 50,000 registros = 99.97% de unicidad.
Solo 16 llamadas comparten telefono con otra llamada en el mismo quarter.

### Impacto en las pruebas

En produccion real, los clientes realizan multiples llamadas. El ratio
real seria del orden de 3-5 llamadas por cliente en promedio (segun
el volumen de 11.6M llamadas y los clientes unicos reales del cliente).

La unicidad artificial del seed significa:
1. `clientes_unicos` en base_ivr_clientes es casi igual al total de llamadas
2. Los tests de clientes unicos (T-034) tienen resultados inflados
3. Las metricas de repeticion de clientes no pueden verificarse con seed

Esto no es un error — es una limitacion conocida del seed generator.
Queda documentado para que los desarrolladores no usen los valores de
`clientes_unicos` del sandbox como referencia de produccion.

## H-ANAL-007 — 12 telefonos aparecen en mas de un segmento

**Severidad: BAJA**

### Datos

```sql
SELECT
    COUNT(DISTINCT cTelefono_Origen) AS count_distinct_global,
    (SELECT clientes_unicos FROM base_ivr_clientes
     WHERE trimestre='Q01_25' AND segmento='nacional_A') +
    (SELECT clientes_unicos FROM base_ivr_clientes
     WHERE trimestre='Q01_25' AND segmento='nacional_B') +
    (SELECT clientes_unicos FROM base_ivr_clientes
     WHERE trimestre='Q01_25' AND segmento='puebla') AS suma_por_segmento
FROM tbl_historico_t1_2025;
```

```
count_distinct_global  suma_por_segmento
49984                  49996
```

`suma_por_segmento (49,996) > count_distinct_global (49,984)` = 12 telefonos
llamaron a DIDs de mas de un segmento en Q1 2025.

### Significado

Esto es comportamiento normal y esperado: un cliente puede llamar al
numero nacional (19028031) y tambien al numero de puebla (19020084)
en el mismo quarter. En ese caso aparece contado en ambos segmentos.

`sp_etl_base_clientes` cuenta `COUNT(DISTINCT cTelefono_Origen)` POR
segmento, no de forma global. La suma de los 3 segmentos puede superar
el total global porque algunos telefonos se cuentan en mas de uno.

Esto no es un error — es el comportamiento correcto del SP y un insight
del negocio. Los 12 telefonos multi-segmento representan clientes que
interactuaron con multiples lineas del IVR.

## H-ANAL-008 — T-057 simulado con SQL; comportamiento Django no validado

**Severidad: BAJA**

### Lo que se hizo

T-057 fue simulado con SQL directo en lugar de Python/Django como
especifica el plan. El plan requiere:

```python
with connections['ivr'].cursor() as c:
    c.execute("INSERT INTO etl_runs ...")
    run_id = c.lastrowid
    ...
```

Lo que se ejecuto fue:

```sql
INSERT INTO etl_runs (...) VALUES (...);
SELECT LAST_INSERT_ID() INTO @run_id;
UPDATE etl_runs SET estado='exitoso' WHERE id=@run_id AND estado='en_ejecucion';
...
SELECT estado AS estado_final FROM etl_runs WHERE id=@run_id;
```

### Que valida y que no valida la simulacion

**Valida:**
- La logica SQL del WHERE en el heartbeat (`AND estado='en_ejecucion'`)
- La idempotencia del UPDATE (ROW_COUNT()=0 cuando estado ya cambio)
- El comportamiento correcto de la tabla etl_runs

**No valida:**
- `cursor.lastrowid` en Django — puede comportarse distinto a `LAST_INSERT_ID()`
  en edge cases (transacciones, auto-commit)
- Connection pooling de Django — si una conexion es reciclada, las variables
  de sesion (como `@run_id`) podrian no persistir entre calls
- El thread del heartbeat en Python/threading — la sincronizacion real
  entre el thread principal y el heartbeat no fue testada

### Accion

La validacion formal de T-057 se completa en Fase 4 (T-055 management command).
La simulacion SQL es suficiente para verificar la logica de base de datos.
