## H-F2-001 — Desviación justificada del plan: captura vs duplicación

**Tipo:** Decisión de implementación  
**Estado:** DOCUMENTADO

### Descripción

El plan `PLAN-CORRECCIONES-EJECUCION-202605101630.md` T-2.1 propone:

```bash
if command -v column &>/dev/null; then
    my_exec -e "SELECT ... FROM seed_executions ..." 2>/dev/null | column -t \
        || log_warn "seed_executions no disponible aun"
else
    my_exec -e "SELECT ... FROM seed_executions ..." 2>/dev/null \
        || log_warn "seed_executions no disponible aun"
fi
```

Este patrón duplica la query SQL completa en ambas ramas. La implementación
real usó un patrón diferente sin duplicación:

```bash
local seed_hist
if seed_hist=$(my_exec -e "SELECT ... FROM seed_executions ..." 2>/dev/null); then
    if command -v column &>/dev/null; then
        echo "${seed_hist}" | column -t
    else
        echo "${seed_hist}"
    fi
else
    log_warn "seed_executions no disponible aun"
fi
```

### Por qué es superior al plan

El patrón del plan mezcla dos responsabilidades en un solo `||`:
- error de la query MySQL (`my_exec` retorna non-zero)
- ausencia del binario `column` (retorna 127)

Con `set -o pipefail`, ambos causan que el pipeline falle y disparan
`log_warn "seed_executions no disponible aun"`. Este es exactamente el
bug original que se estaba corrigiendo (H-EXEC-007).

La implementación con captura separa las responsabilidades:
- `if seed_hist=$(my_exec ...)` — detecta únicamente errores de la query
- `if command -v column` — detecta únicamente la disponibilidad del binario
- El WARN aparece solo cuando la query falla, independientemente de `column`

### Ventajas adicionales

La query SQL solo existe en un lugar. Si en el futuro se modifica la
selección de columnas o el LIMIT, hay un único punto de edición. Con el
patrón del plan, cualquier cambio en la query requeriría editar dos lugares
en el mismo bloque.

## H-F2-002 — `seed_executions` vacía no debe confundirse con tabla ausente

**Tipo:** Comportamiento documentado  
**Estado:** DOCUMENTADO

### Descripción

Durante el Escenario 1, `seed_executions` existía pero tenía 0 filas
(ningún seed exitoso se había completado). El output del script en ese caso:

```
INFO: Ultimas 10 ejecuciones registradas en seed_executions:
[línea en blanco — query devolvió 0 filas]
SUCCESS: Script completado.
```

No se emite WARN porque la query tuvo éxito (exit 0) aunque devolvió
un resultado vacío. Este comportamiento es correcto: la tabla existe y
es accesible, simplemente no tiene registros aún.

### Distinción correcta entre los estados

| Estado | Comportamiento |
|---|---|
| `seed_executions` existe y tiene filas | Muestra filas (con o sin `column`) |
| `seed_executions` existe pero vacía | Línea en blanco, sin WARN |
| `seed_executions` no existe | WARN: `seed_executions no disponible aun` |
| Error de conexión a MariaDB | WARN: `seed_executions no disponible aun` |

La distinción entre "vacía" y "no existe" no requiere mensajes diferentes
en el contexto de este script — ambos estados son transitorios (el seed
se ejecutará y llenará la tabla). La diferencia solo importa para depuración,
y en ese caso el operador puede consultar `information_schema.tables`.

## H-F2-003 — `command -v column` verifica el PATH del proceso en ejecución

**Tipo:** Metodología de testing  
**Estado:** DOCUMENTADO

### Descripción

Para el Escenario 3, se creó un mock de `column` en `/tmp/mock_bin/column`
y se ejecutó el script con `PATH="/tmp/mock_bin:${PATH}"`:

```bash
PATH="/tmp/mock_bin:${PATH}" SKIP_SEED=1 bash provisioners/mariadb/schema_historico.sh
```

La técnica funciona porque `command -v column` busca en el PATH del proceso
actual. Al anteponer `/tmp/mock_bin` al PATH, `command -v column` encuentra
el mock y la rama formateada se ejecuta.

### Limitaciones del mock

El mock usado imprime cada línea con el prefijo `[COLUMN]` para hacer
visible que la rama correcta se ejecutó. En un test más estricto, el mock
debería replicar el comportamiento real de `column -t` (alineación de
columnas por tabuladores). Para los propósitos de este test — verificar
que la rama `column` se activa — el mock es suficiente.

### Herramienta `bats` para tests futuros

Para tests más robustos de funciones bash con dependencias de binarios
externos, la herramienta `bats` (Bash Automated Testing System) permite
crear stubs de comandos de forma controlada sin modificar el PATH del
sistema. Se recomienda evaluar su adopción para los provisioners de IACT-db.

## Impacto de FASE 2

### Antes de FASE 2

```bash
my_exec -e "... FROM seed_executions ..." | column -t \
    || log_warn "seed_executions no disponible aun"
```

En entornos sin `column`:
- La query de `seed_executions` siempre tenía éxito
- `column -t` fallaba con exit 127 (binario no encontrado)
- `set -o pipefail` propagaba el exit 127 del pipeline
- `log_warn "seed_executions no disponible aun"` disparaba
- El operador concluía que la tabla no existía cuando en realidad
  era un binario de formato lo que faltaba

### Después de FASE 2

La causa del WARN está correctamente aislada: solo aparece cuando la
query falla, independientemente de si `column` está disponible o no.
La ausencia de `column` degrada el formato del output a texto plano,
sin afectar la visibilidad del historial de ejecuciones ni los mensajes
de estado.
