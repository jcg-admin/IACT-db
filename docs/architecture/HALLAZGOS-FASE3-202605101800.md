## H-F3-001 — `(( consecutivos++ ))` mata el script con `set -e` en primer ping

**Componente:** `provisioners/mariadb/schema_historico.sh` —
`verificar_estabilidad_mariadb()`  
**Severidad:** ALTA  
**Estado:** RESUELTO (2026-05-10)

### Descripción

Dentro de `verificar_estabilidad_mariadb()`, el primer ping exitoso ejecuta:

```bash
(( consecutivos++ ))
```

Cuando `consecutivos=0`, la expresión aritmética `(( 0 ))` evalúa a falso (exit 1).
Con `set -euo pipefail` activo, el script muere silenciosamente en ese punto.

Comportamiento observado:
```
STEP 3/3 Seed de datos
INFO: Verificando estabilidad de MariaDB
INFO:   Requiere 3 pings exitosos consecutivos
INFO:   Timeout total: 30s
[script termina con exit 1 sin más output]
```

Este es el mismo bug `(( var++ ))` documentado y corregido en `mariadb_wait_ready`
y `postgres_wait_ready` durante sesiones anteriores. No se había detectado en
`verificar_estabilidad_mariadb` porque el seed nunca se ejecutaba (ver H-F3-005).

### Corrección aplicada

```bash
# Antes:
(( consecutivos++ ))

# Después:
# (( ++consecutivos )): pre-incremento — evalúa (( 1 )) → exit 0.
# (( consecutivos++ )) cuando consecutivos=0 evalúa (( 0 )) → exit 1
# y set -e mataría el script silenciosamente en el primer ping exitoso.
(( ++consecutivos ))
```

### Verificación

```bash
bash -c '
set -euo pipefail
consecutivos=0
(( ++consecutivos ))   # → 1 → exit 0 → correcto
echo "consecutivos: ${consecutivos}"
'
# Output: consecutivos: 1
```

## H-F3-002 — `ALTER USER ... mysql_native_password` rompe socket auth sin password

**Componente:** Plan de seguridad `PLAN-SEGURIDAD-MARIADB-202605101715.md` — T-0.2  
**Severidad:** ALTA  
**Estado:** RESUELTO (dual auth aplicado)

### Descripción

T-0.2 del plan de seguridad especificaba:

```sql
ALTER USER 'root'@'localhost'
    IDENTIFIED VIA mysql_native_password
    USING PASSWORD('rootpass123');
```

Al ejecutar este comando, el plugin cambió de `unix_socket` a `mysql_native_password`.
Consecuencia: la autenticación por socket Unix (peer auth) dejó de funcionar sin
password. `provisioners/mariadb/setup.sh` usa `mysql --socket=... -u root`
sin password → FATAL: `No hay acceso root a MariaDB via socket unix`.

El problema es que el plan T-0.2 no consideró que cambiar a `mysql_native_password`
elimina el `unix_socket` plugin, rompiendo el flujo de provisioning que depende
de peer auth por socket.

### Corrección aplicada

Dual auth con `unix_socket OR mysql_native_password`:

```sql
ALTER USER 'root'@'localhost'
    IDENTIFIED VIA unix_socket
    OR mysql_native_password USING PASSWORD('rootpass123');
FLUSH PRIVILEGES;
```

Con esta configuración:
- Socket sin password: funciona (unix_socket peer auth) ✓
- TCP con password: funciona (mysql_native_password) ✓
- authentication_string: hash válido `*AFA7207C...` (no "invalid") ✓

### Impacto sobre el plan de seguridad

El texto de T-0.2 y T-0.4 en `PLAN-SEGURIDAD-MARIADB-202605101715.md` debe
actualizarse: el comando correcto es `IDENTIFIED VIA unix_socket OR mysql_native_password
USING PASSWORD(...)`, no solo `IDENTIFIED VIA mysql_native_password`.

## H-F3-003 — `ERROR 1308: LEAVE with no matching label` en `seed_historico.sql`

**Componente:** `provisioners/mariadb/seed_historico.sql` — stored procedure
`sp_seed_historico`  
**Severidad:** CRÍTICA — el seed no puede ejecutarse  
**Estado:** RESUELTO — seed_historico.sql v3.0.0 usa label `sp_seed_historico: BEGIN ... END sp_seed_historico`. Sin LEAVE/LOOP/ITERATE internos. La causa original era un label faltante; la reescritura del SP en v3.0.0 eliminó el patrón que producía ERROR 1308. Verificado en BD: ejecución exitosa.

### Descripción

Al ejecutar el seed con `my_exec_vars_root`, mysql reporta:

```
ERROR 1308 (42000) at line 85: LEAVE with no matching label: sp_seed_historico
```

El stored procedure `sp_seed_historico` tiene en su cuerpo:

```sql
IF v_count_antes > 0 AND p_force = 0 THEN
    ...
    LEAVE sp_seed_historico;  -- Error aquí: label no reconocido
END IF;
```

`LEAVE sp_seed_historico` es un salto al label del bloque exterior del
procedimiento. Es sintaxis válida de MariaDB dentro de un `BEGIN...END`
etiquetado. El error indica que el cliente mysql no interpretó el SQL como
un único `CREATE PROCEDURE` sino como sentencias separadas, porque el
delimitador `;` dividió el cuerpo del procedimiento.

### Causa raíz

`my_exec_vars_root` usa:

```bash
{ echo "SET @vars..."; cat "$sql_file"; } | mysql --batch --socket=... "$DB_NAME"
```

El comando `DELIMITER $$` en `seed_historico.sql` es una directiva de cliente
mysql (no un statement SQL). En modo `--batch` con input desde pipe, el cliente
NO procesa comandos `DELIMITER`. El resultado: mysql divide el SQL en cada `;`,
enviando el cuerpo del procedimiento como sentencias independientes. `LEAVE`
fuera de un `CREATE PROCEDURE` es inválido → ERROR 1308.

### Impacto de la cadena de bugs enmascarados

Este bug no se había detectado porque:

1. **H-EXEC-009** (SKIP_SEED): el seed siempre se omitía con `SKIP_SEED=0`.
   Al corregirlo en FASE 3, el seed empezó a ejecutarse por primera vez.
2. **H-EXEC-005** (django_user sin CREATE): en ejecuciones anteriores a FASE 1,
   incluso si el seed hubiera corrido, `my_exec_vars` habría fallado en INSERT
   con ERROR 1142.

Este es el tercer bug en la cadena: SKIP_SEED (no corre) → permisos (no inserta)
→ DELIMITER (SP no se crea). Cada uno enmascaraba al siguiente.

### Corrección requerida

Opciones por orden de invasividad:

**Opción A — Reescribir el SP sin DELIMITER:**
Convertir `seed_historico.sql` a un archivo que no use `DELIMITER $$` y en
cambio cree el SP con un cliente que soporte la sintaxis correcta:

```bash
# En lugar de pipe:
mysql --batch --socket=... "$DB_NAME" < "$sql_file"
# Sin pipe — el cliente lee el archivo directamente y procesa DELIMITER
```

**Opción B — Usar un archivo temporal:**
Escribir el SQL a un archivo temporal y ejecutarlo sin pipe, preservando
el procesamiento de `DELIMITER`:

```bash
my_exec_file_root() {
    if [[ -S "${DB_ROOT_SOCK}" ]]; then
        mysql --batch --socket="${DB_ROOT_SOCK}" "${DB_NAME}" < "$1" 2>&1
    fi
}
```

`my_exec_file_root` ya usa este patrón (sin pipe) → funciona correctamente.
El problema es específico de `my_exec_vars_root` que usa pipe para inyectar
las variables de sesión antes del SQL.

**Opción C — Inyectar variables dentro del SQL:**
Hacer que `seed_historico.sql` defina las variables usando los valores del
`.env` directamente (sin variables de sesión `@var`), eliminando la necesidad
de anteponer `SET @SEED_ROWS=...` via pipe.

La opción más limpia es **B + Opción C** combinadas: crear un archivo temporal
con las variables de sesión + el contenido del SQL, luego ejecutarlo con
`mysql --batch` sin pipe.

## H-F3-004 — `log_fatal` no detiene el script en ciertos contextos

**Componente:** `utils/logging.sh` — función `log_fatal`  
**Severidad:** ALTA  
**Estado:** RESUELTO — FASE 4: utils/logging.sh `log_fatal()` hace `log_message ... ; exit 1`. El proceso termina inmediatamente · commit 4ded8ab

### Descripción

El output del seed mostró la siguiente secuencia inesperada:

```
FATAL: Seed incompleto.                ← primer log_fatal (en bloque if)
INFO:  Verificando integridad del seed ← verificar_seed_completo corrió
ERROR: FALLO: tbl_historico_t1_2025...
FATAL: Seed incompleto.                ← segundo log_fatal (en verificar_seed_completo)
SUCCESS: Seed completado y verificado  ← log_success después del if
```

Si `log_fatal` llama `exit 1`, el script debería terminar en el primer FATAL.
Pero tanto `verificar_seed_completo` como `log_success "Seed completado"` se
ejecutaron después.

### Hipótesis sobre la causa

La estructura del código del seed es:

```bash
if ! my_exec_vars_root "$SEED_SQL" | grep -v "^$" | while IFS= read -r line; do
    log_info "  ${line}"
done; then
    log_error "El seed falló..."
    log_fatal "Seed incompleto."  ← ¿está en subshell?
fi

verificar_seed_completo            ← esto corrió aunque FATAL debería haberlo impedido
log_success "Seed completado y verificado"  ← también corrió
```

**Hipótesis 1:** `my_exec_vars_root` retorna exit 0 (mysql devuelve 0 para
ciertos errores SQL). El `if !` condición es FALSE → no entra al `then` block.
El primer FATAL visible no es del `then` block sino de otro contexto.

**Hipótesis 2:** El `while` en el pipeline corre en un subshell. Dentro del
subshell, `log_fatal` llama `exit 1`, que termina el subshell pero no el proceso
padre. El `if` ve el exit del subshell, evalúa la condición, y continúa.

**Hipótesis 3:** `log_fatal` implementa `exit` pero el `set -e` interactúa de
forma inesperada con el bloque `if`.

### Investigación requerida

```bash
# Verificar qué retorna mysql con ERROR 1308
mysql --batch --socket=/run/mysqld/mysqld.sock ivr_legacy \
    -e "LEAVE sp_inexistente;" 2>/dev/null
echo "Exit code: $?"
# Si es 0 → Hipótesis 1 confirmada

# Verificar si log_fatal llama exit
grep -A5 "log_fatal" utils/logging.sh
```

### Impacto

Independientemente de la causa, el script reporta `SUCCESS: Seed completado
y verificado` aunque el seed falló. Esto es un falso positivo que puede
confundir al operador sobre el estado del aprovisionamiento.

## H-F3-005 — El seed nunca fue ejecutado antes: bugs enmascarados en cadena

**Tipo:** Metodología y hallazgo estructural  
**Estado:** DOCUMENTADO

### Descripción

La ejecución de FASE 3 (corrección de H-EXEC-009 / SKIP_SEED) activó el seed
por primera vez. Esto reveló que `seed_historico.sql` y `verificar_estabilidad_mariadb`
tienen bugs que nunca fueron detectados porque el seed estaba permanentemente
bloqueado.

La cadena completa de enmascaramiento:

```
H-EXEC-009 (SKIP_SEED=0 activa --skip-seed)
    ↓ enmascara
H-F3-001 ((( consecutivos++ )) mata el proceso con set -e)
    ↓ ambos enmascaran
H-EXEC-005 (django_user sin CREATE TABLE → tablas históricas no existen)
    ↓ enmascaran
H-F3-003 (LEAVE without label → SP no se crea → seed falla)
    ↓ enmascara
H-F3-004 (log_fatal no detiene el script → falso SUCCESS)
```

Cada bug en la cadena habría impedido descubrir el siguiente.

### Lección

Los tests de integración end-to-end que verifican el estado final (tablas creadas,
datos presentes) son más valiosos que los tests unitarios de componentes individuales
para detectar estos patrones de enmascaramiento en cascada.
