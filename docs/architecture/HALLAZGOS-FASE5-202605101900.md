**Aspecto no verificable (H-F3-003):**

```
INFO:  LEAVE sp_seed_historico;

ERROR: El seed falló o fue interrumpido.
FATAL: Seed incompleto.          ← log_fatal (H-F3-004: no detiene el script)

```

El plan especifica `"Seed completado y verificado"` como verificación de T-5.3.

no detiene el script). El seed histórico no completó porque el stored procedure
`sp_seed_historico` usa `LEAVE sp_seed_historico` que mysql interpreta como
`LEAVE` fuera de un bloque etiquetado cuando el SQL es pasado via pipe.

La distinción correcta:
- FASE 3 verifica que el seed **se intente** → CORRECTO
- H-F3-003 es la razón por la que el seed no **completa** → bug separado

## H-F5-001 — "seed omitido" en T-5.3 es de `schema_seed.sh`, no de `schema_historico.sh`

**Tipo:** Ambigüedad de log  
**Severidad:** MEDIA  
**Estado:** PENDIENTE

### Descripción

En el output de T-5.3 aparece:

```
INFO: Tabla ya tiene 3000 registros — seed omitido (idempotente)
```

Este mensaje viene de `provisioners/mariadb/schema_seed.sh`, que siembra
`tbl_temp_prueba_ivr` (tabla de prueba). La tabla ya tenía 3000 registros
de ejecuciones anteriores, por lo que el seed de prueba se omite correctamente
por idempotencia.

El seed de `schema_historico.sh` para `tbl_historico_*` no tiene este mensaje
porque sí intentó correr (y falló con H-F3-003).

### Problema

Un operador que lee el output completo de `setup.sh mariadb --full` ve
"seed omitido" y puede concluir incorrectamente que el seed histórico fue
omitido. Los dos seeds (`schema_seed.sh` y `schema_historico.sh`) producen
mensajes similares sin distinguir a cuál pertenecen en el contexto de la
salida agregada de provision-mariadb.sh.

### Corrección requerida

Agregar el nombre del componente al mensaje de "seed omitido" en
`schema_seed.sh`:

```bash
# Antes:
log_info "Tabla ya tiene ${count} registros — seed omitido (idempotente)"

# Después:
log_info "schema_seed: tbl_temp_prueba_ivr ya tiene ${count} registros — seed omitido (idempotente)"
```

Y en `schema_historico.sh`:

```bash
# Antes:
log_info "SKIP_SEED=1 — seed omitido."

# Después:
log_info "schema_historico: SKIP_SEED=1 — seed de tbl_historico_* omitido."
```

## H-F5-003 — verify.sh verifica existencia de tablas, no su contenido

**Tipo:** Cobertura de verificación  
**Severidad:** BAJA  
**Estado:** PENDIENTE evaluación

### Descripción

La verificación de tablas históricas en verify.sh 3b usa:

```sql
SELECT COUNT(*) FROM tables
WHERE table_schema='ivr_legacy'
AND table_name LIKE 'tbl_historico_%'
```

Esto cuenta tablas existentes (6 = OK). No verifica si las tablas tienen datos.

En el estado actual tras T-5.3, las 6 tablas existen con 0 rows (el seed
falló por H-F3-003). verify.sh reporta `Tablas históricas presentes: 6`
y EXIT: 0, aunque el pipeline ETL no tenga datos sobre los que operar.

### Evaluación requerida

¿Debe verify.sh verificar también que las tablas históricas tengan datos?

**Argumento a favor:** Un entorno con tablas vacías no es funcional para
el pipeline ETL — equivale a no tener las tablas desde el punto de vista
de negocio.

**Argumento en contra:** La presencia o ausencia de datos es un estado
operacional, no de infraestructura. verify.sh verifica infraestructura.
Un entorno de CI/CD podría tener tablas vacías intencionalmente y aún ser
válido para ejecutar migraciones y pruebas unitarias.

La decisión requiere clarificación del alcance de verify.sh como herramienta.
Por ahora se documenta como pendiente de evaluación, no como bug.
