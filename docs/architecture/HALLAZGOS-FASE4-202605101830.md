## H-F4-001 — `$?` después de pipe captura exit de `grep`, no de `verify.sh`

**Tipo:** Metodología de testing  
**Estado:** DOCUMENTADO

### Descripción

Durante las pruebas se usó inicialmente:

```bash
bash verify.sh 2>&1 | grep -E "históricas|OK:|Errores:"
echo "EXIT: $?"
```

El `$?` capturó el exit code de `grep` (0, porque encontró coincidencias), no
el de `verify.sh`. El output mostraba `EXIT: 0` aunque verify.sh había retornado 1.

### Causa

En bash, `cmd1 | cmd2; echo $?` captura el exit code de `cmd2`, no de `cmd1`.
Para capturar el exit de `cmd1` hay dos alternativas:

```bash
# Alternativa 1: PIPESTATUS
bash verify.sh 2>&1 | grep ...; echo "EXIT: ${PIPESTATUS[0]}"

# Alternativa 2: redirigir a archivo (más legible)
bash verify.sh > /tmp/out.txt 2>&1
echo "EXIT: $?"
grep ... /tmp/out.txt
```

La Alternativa 2 fue la usada para confirmar los exit codes reales en este test.

### Impacto en tests anteriores

Varios tests en sesiones anteriores usaron el patrón `cmd | grep ...; echo "exit:$?"`.
Los exit codes reportados en esos tests correspondían al exit de `grep`, no del
comando principal. Las verificaciones de comportamiento (mensajes de log) son
válidas, pero los exit codes en esos contextos deben considerarse no confiables
como evidencia de corrección.

## H-F4-002 — Contador OK cambia de 25 a 26 al agregar verificación de históricas

**Tipo:** Observación de impacto  
**Estado:** DOCUMENTADO — comportamiento correcto

### Descripción

Antes de FASE 4, `verify.sh` con el entorno completo reportaba:
```
OK: 25  WARN: 0  ERR: 0
```

Después de agregar la verificación de tablas históricas y con las 6 tablas
presentes:
```
OK: 26  WARN: 0  ERR: 0
```

### Por qué es correcto

El nuevo check `ok "Tablas históricas presentes: ${hist_count}"` incrementa
el contador OK cuando las tablas existen. El entorno completo ahora requiere
que las 6 tablas históricas existan para que verify.sh reporte 0 errores.

Cualquier referencia anterior a "25 OK, 0 WARN, 0 ERR" como estado de éxito
debe actualizarse a "26 OK, 0 WARN, 0 ERR".

### Archivos que documentan el estado anterior

- `PLAN-CORRECCIONES-EJECUCION-202605101630.md` — resumen de sesión en contexto
- `HALLAZGOS-EJECUCION-2026-05-10.md` — texto menciona "25 OK"

Estos no requieren corrección activa — son registros históricos. El estado
corriente es 26 OK con entorno completo.

## H-F4-003 — Orden conceptual de verificación: históricas van antes que analíticas

**Tipo:** Arquitectura de verificación  
**Severidad:** BAJA  
**Estado:** RESUELTO — FASE 4: verify.sh reordenado (H-VFY-001). Orden actual: analíticas L205 → funciones L229 → SPs ETL L258 → SPs Reporte L271 → GRANT EXECUTE L284 → históricas L312 · commit 4ded8ab

### Descripción

La verificación actual sigue este orden en la sección 3b:

```
1. Tablas analíticas  (base_ivr_*, job_*, etl_runs)
2. Tablas históricas  (tbl_historico_*)
3. Funciones
4. SPs ETL
5. SPs Reporte
```

El orden correcto desde el punto de vista del pipeline ETL es:

```
1. Tablas históricas  (fuente de datos — sin ellas el ETL no tiene qué procesar)
2. Tablas analíticas  (destino del ETL — se llenan desde las históricas)
3. Funciones
4. SPs ETL
5. SPs Reporte
```

### Por qué no se corrigió en esta FASE

El plan T-4.1 especifica insertar el bloque después de las tablas analíticas.
Cambiar el orden implicaría mover código existente, lo que excede el alcance
de T-4.1. El comportamiento de la verificación es correcto independientemente
del orden — ambas usan `fail` y ambas se verifican siempre.

### Evaluación requerida

Si en una iteración futura se reorganiza la sección 3b, el orden correcto
es históricas → analíticas. La razón: cuando se depura un entorno roto,
ver "tablas históricas faltantes" antes que "tablas analíticas faltantes"
dirige al operador a la causa raíz correcta (el origen), no al síntoma
(el destino del ETL).
